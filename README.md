# crawlkit-testbed

A site with defects planted **on purpose**, and a scorer that measures whether
an audit finds them.

A crawler's value is decided by two numbers nobody publishes: of the defects
that are really there, how many did it find (recall), and of the things it
reports, how many are real (precision). Vendors publish feature counts. This
repo exists to measure the numbers instead.

## How it works

```
site/       static HTML fixtures, one defect family per page, marked with
            <!-- PLANTED: ... --> comments at the exact spot
expected/   manifest.json — what each page SHOULD be flagged for, written by
            hand from the comments, never generated from a crawl
score/      score.py — compares a real audit against the manifest
targets/    live sites registered as additional dogfood targets
```

The manifest describes **defects in plain language** ("duplicate title across
pages"), not auditor code names. `score/defect_to_code.json` maps those to an
auditor's codes. That indirection is what makes the testbed able to score any
auditor — and it stops the commonest way benchmarks rot, which is the
expectation file being generated by the tool it is supposed to judge.

## Scoring

```sh
crawlkit crawl http://localhost:8000/ --max-pages 20 --output run/ --format json
python3 score/score.py --findings run/crawlkit.db
```

Exit 0 when the gates pass, so it can run in CI.

Three rules the scorer enforces, each added after it produced a misleading
number:

1. **Only defects count.** Measurements are facts about the crawl, and scoring
   them would penalise an auditor for honesty.
2. **The negative control defines the noise floor.** `clean.html` plants
   nothing; codes it produces (no response headers on a dev server, no
   sitemap) are environment, not false positives. Without this, precision was
   5% and meaningless.
3. **Crawl-scoped defects are satisfied anywhere in the crawl.** A duplicate
   finding is attributed to whichever page lost the dedupe, and a broken link
   is reported on its 404 target rather than the page linking to it. Pinning
   those to the planting page scores an auditor as wrong for an attribution
   choice.

Recall is the gate. Precision is reported but gated only as a floor, because a
good auditor also reports real defects nobody planted, and those count as
unexpected here by construction.

## Current result

```
recall     92.9%   (26 of 28 planted defects found)
precision   29.5%  (floor 15%)
```

## Known crawlkit gaps this testbed found

Both are real defects, found on the first run, and both are recorded here so
they cannot be quietly forgotten.

1. **Unparseable JSON-LD is invisible.** The parser calls
   `serde_json::from_str` and on `Err(_)` skips the block. A malformed block
   therefore never reaches `structured_data`, and no analyzer can report it —
   a page with broken schema produces no finding at all.

2. **A canonical pointing elsewhere is only detected in the deep profile.**
   `CANSELFRF-V2001` exists and does exactly this, but it is not in the
   default profile, so a default crawl misses a canonical misdirection —
   the single most damaging canonical mistake a site can make.

## Adding a fixture

1. Add `site/whatever.html`, marking each planted defect with a
   `<!-- PLANTED: ... -->` comment at the exact spot.
2. Link it from `site/index.html`. A crawler cannot find what nothing links to.
3. Add an entry to `expected/manifest.json`, written from the comments.
4. If it is a new defect family, add the mapping to
   `score/defect_to_code.json`.
5. Re-run the scorer. A green result that stays green after your change is the
   only evidence that counts.

## Registering a live site

`targets/` holds one file per external site: its URL, what it is built with,
and what it is good at exposing. Live sites are not scored against a manifest —
they are dogfood targets, useful precisely because nobody controlled their
defects.
